Fixed window vs token bucket

An API rate limiter decides, for every request, whether to let it through or reply 429 Too Many Requests. Both limiters below see the same timestamped requests and enforce the same average rate. Step through a scenario and watch where their decisions differ.

How the algorithms work

Fixed window

Request time t falls in window k = floor(t / W), covering [kW, (k+1)W). Keep one counter per window and allow while it's below the limit.

k = floor(t / W)
if k != current: current = k; count = 0
if count < limit: count += 1; allow
else: reject

Boundary problem: the counter forgets everything at the reset, so a full limit just before 10 s plus a full limit just after lets 2× through in a fraction of a second.

Token bucket

Store tokens and when they were last updated. On each request, add what dripped in since then, capped at capacity, then try to spend one.

tokens = min(capacity,
             tokens + (t - last) * rate)
last = t
if tokens >= 1: tokens -= 1; allow
else: reject

Capacity is the largest burst after idling; refill rate is the sustainable average. Fractions are kept: 0.1 s at 0.3 tokens/s adds 0.03.

When to use which

  • Fixed window: coarse quotas where a brief 2× spike is harmless, like "1,000 calls per day" on a billing plan.
  • Token bucket: protecting a service while still allowing normal bursty clients, like a page load firing 5 calls at once. Most API gateways use it.
  • Sliding window variants fix the boundary problem with a little more state.
Distributed rate limiting and Redis

Shared state

With per-gateway counters, a client spread over 10 gateways gets 10× the limit. So counters live in a shared, in-memory store like Redis, keyed by client: rl:{api_key}.

  • Set a TTL on each key so idle clients don't hold memory forever.
  • Use one trusted clock, such as Redis TIME, to avoid skew between gateways.

Atomic updates

Read-then-write races: two gateways both read tokens = 1 and both allow. A Lua script runs as one atomic step, so the second request sees 0.

-- token bucket as one atomic Redis script
local b = redis.call("HMGET", KEYS[1], "tokens", "ts")
local tokens = tonumber(b[1]) or capacity
local ts = tonumber(b[2]) or now
tokens = math.min(capacity, tokens + (now - ts) * rate)
local ok = tokens >= 1
if ok then tokens = tokens - 1 end
redis.call("HSET", KEYS[1], "tokens", tokens, "ts", now)
redis.call("EXPIRE", KEYS[1], ttl)
return ok and 1 or 0

Fixed window needs no script: INCR is atomic, so allow = INCR(key) <= limit.
